소프트웨어 개발은 코드베이스에 변경을 가하는 작업의 연속입니다. 변경을 가해도 변경을 가하기 전 동작들이 정상적으로 동작하는 것이 보장한다는 것을 확인시켜주는 고마운 장치가 소프트웨어 테스트입니다. 변경 후 이전 동작들이 혹은 변경한 기능이 의도대로 동작하는지 확인하는 절차들은 모두 테스트에 해당합니다. 웹앱이라면 로컬서버를 띄워서 UI에 클릭을 하고, 실패하면 로그를 탐색하는 이런 작업 역시 테스트입니다. 다만, 이런 수동 테스트는 비효율적이므로 개발자들의 노력으로 자동화 가능한 테스트들이 탄생했습니다. 그 중 가장 큰 갈래인
**전통적인 테스트**와 **프로덕션 테스트** 대해 알아보겠습니다.

## 1. 전통적인 테스트
전통적인 테스트는 소프트웨어 개발 도중 소프트웨어가 의도한 동작을 수행하는지 여부를 평가하며 '소프트웨어 테스트'라고 하면 일반적으로 전통적인 테스트를 의미하는 경우가 많습니다. 배포하기 전에 테스트를 수행하며 [단위테스트 -> 통합 테스트 -> 시스템 테스트] 계층 구조를 이룹니다. 

### 단위 테스트
TDD(Test-Driven Dev)에서 필수적으로 사용되는 테스트입니다. 가장 기본 단위가 되는 테스트이며 시스템 내에서 동작하는 함수나 클래스 등을 독립적으로 각자 테스트하는 방식입니다. 단위 테스트 자체가 해당 함수나 모듈이 시스템이 요구하는 동작을 수행하는지에 대한 명세가 되기도 합니다.

### 통합 테스트
단위 테스트는 외부 의존성을 배제하고 하나의 클래스나 함수 같은 가장 작은 코드 단위를 독립적으로 검증합니다. 반면 통합 테스트는 데이터베이스, 네트워크, 모듈 간의 연동처럼 여러 구성 요소가 함께 결합되어 올바르게 작동하는지 확인합니다. 따라서 단위 테스트는 빠른 피드백과 정확한 버그 위치 파악에 유리하고, 통합 테스트는 시스템 전체의 실제 동작 흐름을 보장하는 데 목적이 있습니다. 따라서, 실제 동작 흐름을 보기 위해 의존성을 어떻게 주입할 것인지도 고려 대상이다.

### 시스템 테스트
아직 배포하지 않은 시스템을 테스트하는 가장 큰 규모의 테스트입니다. 

#### smoke test
DB 조회, 핵심 비즈니스 로직 동작 등 최소한의 핵심 기능들이 동작하는지 빠르게 보기 위한 테스트입니다. 시스템 테스트의 첫 관문으로 상세 테스트를 수행하기 전 수행되는 게이트키퍼 역할을 합니다. 전자 회로에 전원을 처음 넣었을 때 연기가 나는지 확인하는 데서 유래한 명칭입니다. 

#### performance test
기능 동작 여부를 넘어서 요구 스펙에 맞는 성능 범위 내에서 동작하는지를 검증하는 테스트입니다. 요구 응답시간이 50ms이내라면, 시스템이 동작할 때 실제 응답 시간을 측정하여 요구 응답 시간을 만족하는지 등을 검증하는 테스트입니다. 응답 시간뿐만 아니라 cpu, memory, 추론 시간 등 요구 스펙에 관련되며 측정가능한 지표들을 테스트합니다.

#### regression test
regression test(회귀 테스트) 테스트 범위가 아니라 테스트 목적 관점에서 유래한 이름이다. 코드에 변경을 가했을 때 기존 동작도 여전히 계속 정상 동작하는지를 확인하기 위한 목적의 테스트를 회귀테스트라고 합니다. 그러니까, 회귀 테스트를 구현하기 위해 단위 테스트도 쓰일 수 있고, 통합 테스트도 쓰일 수 있고, 스모크 테스트도 쓰일 수 있습니다. 방법론이라기보다 테스트의 특정 목적을 강조하는 용어입니다.

## 2. 프로덕션 테스트
이전에 언급한 테스트들은 밀폐된 테스트 환경에서 수행됩니다. 하지만 프로덕션 테스트는 실제 배포되어 서비스 중인 프로덕션 시스템을 대상으로 이루어지는 테스트입니다. ML 도메인으로 따지면 오프라인/온라인 테스트와 유사합니다.

### config test
구글 같이 초대형 시스템에서는 코드 배포 없이 서비스를 제어하기 위해 system config를 코드와 분리하여 관리합니다. 잘못된 config 값 하나가 끼어서 배포되면 전체 서비스가 마비될 위험이 있기 때문에 코드와 마찬가지로 config도 테스트를 수행합니다. 특히 config 수가 수동으로 검증하기 어려울만큼 방대한 경우엔 더더욱 코드처럼 config도 자동화할 수 있는 테스트 환경에 편입되어야 합니다.

### stress test
모든 코드와 config가 의도대로 요구 성능 범위 내에서 동작하더라도 cpu 과부하나 out-of-memory 같은 이슈로 시스템이 뻗어버릴 수 있습니다. 따라서, DB 용량이 어느정도 되어야 쓰기 작업이 실패하는지, 서버는 초당 몇 개의 쿼리를 응답할 수 있는지 등의 테스트를 수행하여 매끄럽고 장애 없이 동작하는 스트레스 범위를 측정할 필요가 있습니다.

### canary test
예전 석탄 광부들이 광산 깊은 곳에 작업하러 들어가기 전 canary(새) 한 마리를 보내어서 죽는지 확인하는 방식으로 유독가스 여부를 확인하던 방식에서 유래한 이름입니다. 전체 서버에 새로운 버전을 배포하기 전에 아주 작은 일부 서버에만 시험 삼아 배포해보는 테스트입니다. 문제가 발생하더라도 대부분 서버에서는 기존 stable 버전이 배포되어있기 때문에 큰 문제가 없습니다. 
다만, canary test는 다른 테스트들과는 조금 성격이 다른 부분이 있습니다. 지금까지 보지 못 했던 코드 상의 문제점을 찾는다던가 하는 등 코드를 대상으로 하는 테스트라기보다 해당 버전을 배포했을 때 기존 버전보다 사용자들의 트래픽이나 반응에 변화가 있는지를 보기 위한 성격이 짙습니다. 따라서, 이름이 테스트이긴 하나 위에서 언급한 소프트웨어를 위한 테스트뿐만 아니라 A/B 테스트를 위한 수단의 성격도 가지고 있습니다.

## 3. 마무리
테스트를 수행한다고 모든 문제점을 조기에 찾아서 해결할 수 있는 것은 아닙니다. 아무리 테스트를 해도 버그는 아직 발견되지 않은 것이지 모든 소프트웨어는 알게 모르게 버그를 내포하고 있습니다. 그럼에도 테스트를 해야하는 이유는 적어도 우리가 찾지 못한 버그가 발생할 수 있는 영역의 넓이를 줄여나가기 위함입니다. '적어도 우리가 작성한 테스트 범위 내에서는 문제가 발생하지 않을 것이다!'라는 심리적 안전감이 두려움 없이 프로덕션 배포 버튼을 누를 수 있게 해주는 최소한의 장치라고 봐야하며, 이건 큰 역할입니다.
