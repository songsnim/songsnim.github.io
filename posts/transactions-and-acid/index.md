## 트랜잭션
결제 정보가 중간에 사라지거나, 항공권 예매가 중복으로 처리되는 등의 **동시성** 문제를 해결하기 위해 **트랜잭션** 개념을 사용합니다.
트랜잭션이란 DB 상태를 변경하기 위해 수행하는 **하나의 논리적 작업 단위**입니다. "계좌이체"라는 하나의 논리적 작업을 위해 'A계좌에서 출금'과 'B계좌로 입금'이라는 두 개의 연산이 함께 성공하거나, 함께 실패해야 하는 것처럼 여러 연산이 하나의 공동체로 묶이는 것을 트랜잭션이라고 합니다.
단, 해당 트랜잭션의 안전을 보장하기 위해 **ACID 원칙**을 만족해야 합니다.

## 1. A: Atomicity(원자성) 
더 이상 쪼갤 수 없는 원자처럼 트랜잭션에 포함된 **모든 연산이 전부 성공하거나, 하니면 전부 실행 이전 상태로 돌아가는 것을 보장**하는 원칙입니다. 돈이 출금은 되었는데, 받는 계좌에서 입금은 되지 않아 돈이 증발하는 사태를 막아줍니다.
보통 **트랜잭션 로그**를 통해 구현되며 실제 데이터 변경을 발생시키기 전에 먼저 변경 내용을 로그에 기록하고, 문제가 발생하면 해당 로그를 참조해 원래 상태로 **롤백**합니다. 모든 작업이 성공적으로 완료되었을 때만 해당 변경사항을 **커밋**합니다.

## 2. C: Consistency(일관성)
트랜잭션이 성공하던 말던 DB는 항상 정해진 규칙과 제약조건을 만족하는 유효한 상태여야 합니다. 
예를 들어서, 
- 규칙 1: 계좌의 잔액은 음수가 될 수 없다
- 규칙 2: 모든 계좌의 총합은 변하지 않아야 한다.

이 경우 잔액이 3000원인데 5000원을 이체하려는 트랜잭션이 시도된다면, 해당 트랜잭션은 '규칙 1'을 위반하게 되므로 **consistency** 원칙에 따라 해당 트랜잭션 커밋을 거부하고 롤백해 **DB의 유효한 상태를 보호**합니다.

## 3. I: Isolation(고립성) 
**고립성**이란 여러 트랜잭션이 동시에 실행될 때, 서로 영향을 주지 않고 독립적으로 실행되는 것처럼 보이게 하는 원칙입니다.
화장실에 누가 들어가 문을 잠그면, 다음 사람은 그 사람이 나올 때까지 밖에서 기다려야 하는 것과 같습니다.
먼저 데이터에 접근하는 순간 데이터를 **Lock**하여, 해당 트랜잭션이 끝날 때까지 다른 트랜잭션은 접근하지 못 하고 대기하는 방식으로 구현됩니다.

## 4. D: Durability(지속성) 
성공적으로 커밋된 트랜잭션 결과는 시스템에 영구적으로 저장되며, 이후 정전이나 서버 다운이 발생해도 데이터가 손실되지 않음을 보장하는 원칙입니다.

DB가 변경 내용을 비휘발성 메모리(HDD, SSD)에 기록함으로써 가능한데, 보통 시스템은 성능때문에 RAM에서 데이터 작업을 처리하지만 커밋이 발생하는 순간 변경 내용이 담긴 로그는 반드시 HDD나 SSD에 저장합니다. 
심지어 트랜잭션 도중에 서버가 터지더라도 해당 로그가 남아있기 때문에 롤백이 가능합니다.
